1Quick Start

Не вибираєш розмір наперед. Workflow сам класифікує задачу на SMALL · MEDIUM · FULL після Phase 1 і пройде відповідний шлях.

Який скіл обрати?

Якщо задача — це...Скіл
Реструктуризація існуючого коду без нової поведінки (rename, split, extract, FSD migration, cross-platform unify)/refactoring-workflow
Нова функціональність (новий екран, API endpoint, saga, FF rollout, інтеграція)/new-feature-workflow
І те, і інше в одному тікетіРозділити на 2 тікети. Refactor PR і feature PR мають різні review profiles — змішування ламає review дисципліну.
💡 Не парся над розміром
Phase 0 (audit) запускається завжди — навіть для того, що виглядає 5-хвилинним. 1 хв insurance проти години пошуку hidden dependency.

2The 5-Step Flow

Що ти бачиш, коли інвокаєш скіл — від першої команди до зеленого MR.

  1. Інвокація ~5 sec

    Пишеш у Claude Code: /refactoring-workflow TICKET-123 Unify PaymentForm component — і повертаєшся пити каву.

  2. Phase 0 — Audit (always-on) ~1–3 min

    Запускається pre-flight-auditor (refactor) або feature-reuse-auditor (feature). Шукає hidden deps, схожі фічі, reuse-кандидати.

    Ти отримуєш: файл specs/{ticket}/pre-flight.md або reuse-audit.md + питання “підтверджуєш scope?”

  3. Phase 1 — Requirements + Mode Classification ~5–10 min

    requirements-agent пише requirements.md з трьома секціями:

    • User Stories + EARS criteria
    • § Delivery Model (single-MR / stacked / multi-MR)
    • § Complexity Classification з Mode: SMALL | MEDIUM | FULL

    🚪 USER GATE Підтверджуєш або редагуєш Mode: руками.

  4. Phase 2–7 — Auto-execution за Mode варіюється

    Orchestrator читає Mode: і виконує тільки потрібні фази (див. Switchboard нижче). Approval gates з’являються тільки на FULL (Phase 2/3) і на D-decision blockers.

  5. Done commit + MR

    SMALL ≈ 15-30 хв, MEDIUM ≈ 1-2 год, FULL ≈ години-дні (за Delivery Model). На виході: PR(и) + history.md (MEDIUM/FULL) або 1-параграф ретро в commit message (SMALL).

4Walkthroughs — два кейси

Що ти реально бачиш у консолі. Перемикай таби нижче.

"Rename formatPrice → formatCurrency у 2 файлах"

  • ~5 sec Ти: /refactoring-workflow Rename formatPrice → formatCurrency
  • ~1 min Phase 0 · pre-flight-auditor → 0 hidden deps, 2 caller files
  • ~5 min Phase 1 · requirements.md з Mode: SMALL
  • gate Ти: "ok"
  • skip Phase 2 — Design
  • skip Phase 3 — Tasks
  • ~2 min Phase 4 · quick-implementor робить rename + править 2 каллери
  • ~1 min Phase 5 · tsc + lint + test + build → all green
  • ~1 min Phase 6 · 1 commit + glab mr create
  • done Phase 7 · 1-параграф ретро в commit message

Загалом ~10 хв активного часу. Файли в specs/: тільки pre-flight.md + requirements.md. Жодного design.md / tasks.md / history.md.

"New upsell screen + new endpoint + variation FF"

  • ~5 sec Ти: /new-feature-workflow TICKET-456 Upsell screen with variation FF
  • ~3 min Phase 0 · feature-reuse-auditor → 4 REUSE candidates, 6 integration touchpoints, FF strategy = variation-based
  • gate Ти: апрувиш scope
  • ~10 min Phase 1 · requirements.md з 5 user stories + Mode: FULL (тригер: FF wiring + new endpoint + multi-slice)
  • gate Ти: "ok, FULL правильний"
  • ~15 min Phase 2 · design.md з Component Shape + API Contract + State Shape + FF Wiring + Loading/Error
  • gate Ти: апрувиш design
  • ~10 min Phase 3 · tasks.md з 3 vertical slices + §F1/§F2/§F3
  • gate Ти: апрувиш tasks
  • ~25 min Phase 4 · Slice 1 · spec-implementor → ✅ COMPLETED
  • block Phase 4 · Slice 2 · 🛑 BLOCKED — "API Contract ambiguous on retry policy"
  • gate Ти: обираєш option 1 → orchestrator commits D3 → resume
  • ~30 min Phase 4 · Slice 2 · resumed → ✅ COMPLETED
  • ~25 min Phase 4 · Slice 3 · ✅ COMPLETED
  • ~20 min Phase 5 · tsc + lint + jest + builds + spec-coverage-verifier + ручний click-through (golden + slow network + error + cycle через FF варіанти)
  • ~15 min Phase 6 · docs-sync commit → release merge → conflict resolve → push → glab mr create
  • done Phase 7 · history.md + Skill calibration section (важливо — feature mode experimental)

Загалом ~3-4 год активної взаємодії, розкидано на 1-2 дні. На виході: specs/ з усіма артефактами + 1 PR (за Delivery Model).

5D-Decision Blockers (FULL mode escalation)

Коли spec-implementor зустрічає невирішену неоднозначність — він зупиняється і ескалює до тебе. Не auto-resolve. Так працює spec-first дисципліна.

Як виглядає blocker

🛑 BLOCKED — Slice 2, Layer "API client"

Blocker class:     B (API contract ambiguity)
Divergence:        backend doc каже retry on 503,
                   але не вказує backoff strategy
D-decisions used:  D1, D2 — none applied
Proposed options:
  1. Exponential backoff (1s, 2s, 4s, max 3 attempts)
  2. Manual retry only (no auto)
  3. Defer to product call

Recommendation:    Option 1

Awaiting D-decision approval before resuming slice 2.

Що ти робиш

  1. Обираєш одну з опцій (або кажеш свою)
  2. Orchestrator редагує design.md додаючи новий блок ### D3 — Retry policy з Decision / Rationale / Affected components
  3. Orchestrator робить commit: chore: add D3 retry policy
  4. Тільки потім resume агента: "D3 approved, resume slice 2 from blocker"
🔒 Чому саме так

Spec оновлюється перед кодом, що його реалізує. Жодного spec drift, повна аудит-стежка. Якщо через 6 місяців хтось питає "чого тут exponential backoff" — відповідь у design.md → §Decisions → D3.

6Mis-classification Playbook

LLM-класифікація може помилитись. User Gate — твій cheap override.

Сценарій 1: Mode здається занизьким

Класифікатор каже SMALL, але ти знаєш що там cross-platform divergence.

Дія: На Phase 1 user gate редагуєш Mode: SMALL → Mode: FULL у requirements.md. Orchestrator перекалібрується автоматично.

Сценарій 2: Mode здається завищеним

Класифікатор поставив FULL, але ти бачиш що це чесно 2 файли.

Дія: Те ж саме — едітиш Mode: руками. Phase 2/3 будуть пропущені/спрощені.

Сценарій 3: Mid-flight зрозумів що Mode неправильний

Phase 4 implementation: quick-implementor повідомляє "файлів стало >3, треба MEDIUM".

Дія:

  1. Зупиняєш агента
  2. Повертаєшся на Phase 1, редагуєш Mode: в requirements.md
  3. Orchestrator резюмує з потрібної фази (наприклад, тепер потрібен design.md → запускає Phase 2)
❌ Не "докручувати specs на льоту"
Заборонено додавати design.md вручну посеред Phase 4 без переходу через Phase 1. Це spec drift — і це причина 90% катастроф у refactor-флоу.

7Do / Don't

✓ Що ти робиш руками

  • Обираєш /refactoring-workflow vs /new-feature-workflow за типом задачі
  • Затверджуєш user gates (Phase 0 scope, Phase 1 requirements + Mode, FULL: Phase 2 design, Phase 3 tasks)
  • Вирішуєш D-decision blockers (FULL mode)
  • Робиш ручний click-through після implementation
  • Якщо Mode неправильний — едітиш Mode: у requirements.md і даєш orchestrator перерахуватись
  • Запускаєш Phase 7 retrospective навіть для невеликих задач — lessons compound

✗ Чого ти НЕ робиш руками

  • Не пишеш requirements.md / design.md / tasks.md / pre-flight.md / history.md сам — це роблять агенти
  • Не імплементиш кластери прямо — це робить spec-implementor
  • Не пропускаєш Phase 0 навіть для тривіальної задачі
  • Не апрувиш SCSS verbatim copy — має бути breakpoint mixin / variant prop / D-decision (FULL)
  • Не робиш pivot Delivery Model на льоту — re-run Phase 1
  • Не маркуєш feature слайс done поки entry point не wired (§F1 step 7) — це completion bias

8Tips з практики

🟢 Phase 0 завжди

1 хв insurance vs година пошуку hidden dep. Вірю в "always-on audit" сильніше після post-mortem великого cross-platform рефакторингу.

🟡 Mode — не закон

Якщо рубрика каже FULL, але ти бачиш що задача дрібна — едітиш на MEDIUM. User-override > LLM-класифікація.

🔵 D-decisions кумулюються

Кожне рішення в design.md стає reference для наступних рефакторів. Не пропускай їх "усно".

🟣 Skill calibration критична

FULL feature mode — experimental. history.md Skill calibration section — це вхід в v2 правил. Без нього experimental не покращується.

⚫ Поганий результат = сигнал до правил

Не вініть агентів — записуй в Skill calibration що пішло не так, оновлюємо правила в скілі. Workflow має еволюціонувати.

🔵 Не змішуй refactor + feature у одному PR

Це різні review profiles. Зміни паралельно у двох воркфлоу + двох PR.
